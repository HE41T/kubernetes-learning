# บทที่ 8: Pod แบบหลายคอนเทนเนอร์ (Multi-Container Pods)

## บทนำ

ในบทที่ 5 ได้อธิบายการจัดการ **Pod แบบคอนเทนเนอร์เดียว** ซึ่งถือเป็นแนวทางปกติในการใช้งาน Kubernetes เนื่องจากโดยทั่วไปเรามักรัน **หนึ่งไมโครเซอร์วิสต่อหนึ่ง Pod** เพื่อส่งเสริมการแยกส่วนความรับผิดชอบ (Separation of Concerns) และเพิ่มความสอดคล้องภายใน (Cohesion)

อย่างไรก็ตาม ในเชิงเทคนิคแล้ว **Pod สามารถประกอบด้วยคอนเทนเนอร์ได้มากกว่าหนึ่งตัว** ซึ่งเปิดโอกาสให้เกิดรูปแบบการออกแบบ (Design Patterns) ที่สำคัญใน Kubernetes

ในบทนี้จะอธิบาย:

* เหตุผลที่ต้องใช้ Pod แบบหลายคอนเทนเนอร์
* กรณีการใช้งานที่เหมาะสม
* รูปแบบการออกแบบที่พบบ่อย เช่น Init Container, Sidecar และรูปแบบอื่น ๆ ที่ระบุอยู่ในโครงร่างการสอบ

---

## การทำงานกับหลายคอนเทนเนอร์ในหนึ่ง Pod

สำหรับผู้เริ่มต้น Kubernetes การออกแบบ Pod อาจไม่ชัดเจนในช่วงแรก เมื่อศึกษาจากเอกสารหรือบทเรียน คุณจะพบว่า Kubernetes อนุญาตให้รันหลายคอนเทนเนอร์ภายใน Pod เดียวกันได้

คำถามที่มักเกิดขึ้นคือ:

> ควรรวมไมโครเซอร์วิสหลายตัวไว้ใน Pod เดียว หรือควรแยกเป็นหลาย Pod?

คำตอบโดยสรุปคือ **ควรใช้หนึ่งไมโครเซอร์วิสต่อหนึ่ง Pod** เนื่องจากแนวทางนี้:

* สนับสนุนสถาปัตยกรรมแบบกระจายศูนย์ (Decentralized)
* ลดการพึ่งพากัน (Decoupled)
* เพิ่มความสามารถในการปรับขยายและอัปเดตระบบ

คุณสามารถอัปเดตหรือรีสตาร์ทไมโครเซอร์วิสหนึ่งตัวได้ โดยไม่กระทบส่วนอื่นของระบบ

---

## เหตุผลในการใช้ Pod แบบหลายคอนเทนเนอร์

แม้จะนิยมใช้หนึ่งไมโครเซอร์วิสต่อหนึ่ง Pod แต่การรันหลายคอนเทนเนอร์ใน Pod เดียวกันก็มีความจำเป็นในบางกรณี โดยทั่วไปแบ่งได้เป็น 2 กลุ่มหลัก

### 1. การเตรียมความพร้อม (Initialization)

ใช้สำหรับรันลอจิกเตรียมระบบ เช่น:

* การตั้งค่าไฟล์
* การดาวน์โหลดข้อมูล
* การตรวจสอบเงื่อนไขก่อนเริ่มแอปพลิเคชัน

ลอจิกประเภทนี้จะถูกรันใน **Init Container**

### 2. ฟังก์ชันเสริม (Helper Functionality)

เป็นการเพิ่มความสามารถให้แอปพลิเคชันหลัก โดยไม่ต้องเขียนโค้ดเพิ่มในตัวแอป เช่น:

* การจัดการ Log
* การซิงโครไนซ์ไฟล์
* การตรวจสอบหรือเฝ้าดูสถานะ

คอนเทนเนอร์ประเภทนี้เรียกว่า **Sidecar Container**

---

## Init Containers

**Init Container** ใช้สำหรับเตรียมความพร้อมก่อนที่คอนเทนเนอร์แอปพลิเคชันหลักจะเริ่มทำงาน

หากเปรียบเทียบกับภาษาโปรแกรม:

* คล้ายกับ Constructor หรือ Static Initialization Block ในภาษา Java หรือ C++
* ใช้สำหรับตรวจสอบข้อมูลและตั้งค่าสภาพแวดล้อมเริ่มต้น

### ลักษณะการทำงานของ Init Containers

* รันก่อนคอนเทนเนอร์หลักเสมอ
* มีวงจรชีวิตเป็นของตัวเอง
* สามารถกำหนดหลาย Init Container ได้
* ระบบจะรันตามลำดับที่ระบุใน Manifest

หาก Init Container ตัวใดล้มเหลว:

* Pod ทั้งหมดจะถูกรีสตาร์ท
* Init Containers จะถูกรันใหม่ตั้งแต่ต้นตามลำดับ

ดังนั้น ลอจิกใน Init Container ควรเป็นแบบ **Idempotent** คือสามารถรันซ้ำได้โดยไม่ก่อให้เกิดผลเสีย

### การกำหนดค่า Init Containers

Init Containers จะถูกกำหนดในส่วน:

```yaml
spec:
  initContainers:
```

ซึ่งแยกออกจากส่วน `spec.containers` ของคอนเทนเนอร์หลักอย่างชัดเจน

## The Sidecar Pattern

ต่างจาก Init Container ที่รันแล้วจบ **Sidecar Container** จะรันควบคู่ไปกับแอปพลิเคชันหลักตลอดอายุของ Pod

แนวคิดหลักคือการแบ่งบทบาทของคอนเทนเนอร์ออกเป็น:

* คอนเทนเนอร์แอปพลิเคชันหลัก
* คอนเทนเนอร์ที่มอบฟังก์ชันเสริม

ตัวอย่างการใช้งาน Sidecar:

* การจัดการ Log
* การซิงโครไนซ์ไฟล์
* การเฝ้าดูการเปลี่ยนแปลง (Watcher)

Sidecar จะไม่เป็นส่วนหนึ่งของ API หรือทราฟฟิกหลักของแอปพลิเคชัน แต่จะทำงานแบบ **Asynchronous** และมักใช้ Volume ร่วมกับคอนเทนเนอร์หลัก

---

## The Adapter Pattern

ปัญหาที่พบบ่อยในการพัฒนาแอปพลิเคชันคือ **Cross-cutting Concerns** เช่น:

* รูปแบบ Log
* โครงสร้างข้อมูลสำหรับ Monitoring

หากฝังลอจิกเหล่านี้ไว้ในโค้ดของแอป จะทำให้โค้ดซับซ้อนและต้องเขียนซ้ำหลายครั้ง

**Adapter Pattern** ช่วยแก้ปัญหานี้โดย:

* ให้คอนเทนเนอร์หลักสร้างข้อมูลในรูปแบบของตัวเอง
* ใช้ Adapter Container แปลงข้อมูลให้อยู่ในรูปแบบที่ระบบภายนอกต้องการ

คอนเทนเนอร์ทั้งสองจะสื่อสารกันผ่าน **Volume ที่ใช้ร่วมกัน** ทำให้แอปพลิเคชันหลักไม่ต้องรับรู้รายละเอียดของระบบภายนอก

---

## The Ambassador Pattern

**Ambassador Pattern** เป็นรูปแบบที่ใช้คอนเทนเนอร์หนึ่งทำหน้าที่เป็น Proxy สำหรับการสื่อสารกับบริการภายนอก

หน้าที่หลักของ Ambassador ได้แก่:

* จัดการ Retry logic
* ดูแล Authentication และ Authorization
* ตรวจสอบ Latency และความเสถียรของการเชื่อมต่อ

ข้อดีของรูปแบบนี้คือ:

* ซ่อนความซับซ้อนของการสื่อสารภายนอกจากแอปพลิเคชันหลัก
* แอปพลิเคชันหลักสื่อสารผ่าน `localhost` ได้โดยตรง
* ลดภาระและความซับซ้อนในโค้ดของแอปพลิเคชัน

---

## สรุป

* Pod สามารถรันได้หลายคอนเทนเนอร์ แต่ไม่ควรใช้แทนการแยกไมโครเซอร์วิส
* หนึ่งไมโครเซอร์วิสต่อหนึ่ง Pod ยังคงเป็นแนวทางหลัก
* Multi-Container Pods เหมาะกับลอจิกเตรียมระบบและฟังก์ชันเสริม
* Init Container ใช้สำหรับการเตรียมความพร้อมก่อนเริ่มงาน
* Sidecar, Adapter และ Ambassador เป็นรูปแบบการออกแบบที่ช่วยลดความซับซ้อนของแอปพลิเคชัน

การเข้าใจรูปแบบเหล่านี้จะช่วยให้คุณออกแบบ Pod ได้เหมาะสม มีโครงสร้างที่ยืดหยุ่น และสอดคล้องกับแนวคิดของ Kubernetes
