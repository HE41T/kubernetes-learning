# บทที่ 3: การโต้ตอบกับ Kubernetes (Interacting with Kubernetes)

ในฐานะนักพัฒนาแอปพลิเคชัน คุณจะต้องโต้ตอบกับคลัสเตอร์เพื่อจัดการ Object ต่าง ๆ  
ทุกการเรียกใช้งานจะถูกรับและประมวลผลโดย **API server**  
ซึ่งสามารถทำได้หลายวิธี เช่น ผ่าน **Dashboard**, เครื่องมือบรรทัดคำสั่งอย่าง **kubectl** หรือส่งคำขอ HTTPS โดยตรงไปยัง API endpoints

> สำหรับการสอบ จะไม่มีการทดสอบการใช้งานผ่าน UI (Dashboard)  
> เครื่องมือเดียวที่คุณต้องใช้คือ **kubectl**

---

## พื้นฐานของ API (API Primitives and Objects)

**Primitives** คือหน่วยพื้นฐานในการสร้างและรันแอปพลิเคชันบน Kubernetes เช่น Pod, Deployment และ Service  

- เปรียบเทียบกับ **OOP (Object-Oriented Programming):**
  - Primitive ≈ Class (พิมพ์เขียวของคุณสมบัติและพฤติกรรม)
  - Object ≈ Instance (อินสแตนซ์ที่ถูกสร้างจริง มีสถานะเป็นของตัวเอง)
- ทุก Object จะมี **UID (Unique Identifier)** อัตโนมัติ เพื่อแยกแยะแต่ละ Object

---

## โครงสร้างของ Object

ทุก Object ใช้ไฟล์ **YAML** เป็นหลักในการกำหนดค่า (Manifest) ประกอบด้วย:

- `apiVersion`: เวอร์ชันของ API ที่ใช้ตรวจสอบความถูกต้อง
- `kind`: ประเภทของ Primitive (เช่น Pod หรือ Service)
- `metadata`: ข้อมูลระดับสูง เช่น ชื่อ (Name), Namespace, Label
- `spec (Specification)`: การประกาศ "สถานะที่ต้องการ" เช่น อิมเมจที่ใช้, ค่าสภาพแวดล้อม
- `status`: สถานะปัจจุบันของ Object (Kubernetes จะปรับให้ตรงกับ spec)

---

## การใช้งาน kubectl

รูปแบบพื้นฐาน:

```bash
kubectl [คำสั่ง] [ประเภททรัพยากร] [ชื่อทรัพยากร] [แฟล็กเสริม]
```

- **คำสั่ง (Command)**: เช่น create, get, describe, delete
- **ประเภททรัพยากร (TYPE)**: เช่น pod หรือชื่อย่ออย่าง svc (สำหรับ Service)
- **ชื่อ (NAME)**: ชื่อที่คุณตั้งให้ Object (ระบุใน metadata.name)
- **แฟล็ก (Flags)**: เช่น `--port=80` หรือ `-o yaml` เพื่อกำหนดรายละเอียดเพิ่มเติม

---

## แนวทางการจัดการ Object (Managing Objects)

มี 2 วิธีหลัก:

### 1. การจัดการแบบคำสั่ง (Imperative Management)

เป็นการสั่งงานโดยตรงผ่านคำสั่ง `kubectl` โดยไม่ต้องเขียนไฟล์ Manifest (ไฟล์ YAML)

- **การสร้าง**: ใช้คำสั่ง `kubectl run` หรือ `kubectl create`
    - ข้อดี: รวดเร็ว ไม่ต้องวุ่นวายกับโครงสร้างไฟล์ YAML
- **การอัปเดต**: ใช้คำสั่ง `kubectl edit` (เปิดเอดิเตอร์เพื่อแก้คอนฟิกสด) หรือ `kubectl patch` (แก้ไขเฉพาะบางส่วนด้วย JSON)
- **การลบ**: ใช้คำสั่ง `kubectl delete` (ปกติจะลบแบบ Graceful หรือรอให้ระบบปิดตัวลงอย่างนุ่มนวลประมาณ 30 วินาที แต่ในการสอบสามารถใช้ `--now` เพื่อบังคับลบทันทีเพื่อประหยัดเวลา)

### 2. การจัดการแบบประกาศ (Declarative Management)

เป็นการใช้งานผ่านไฟล์ Manifest (YAML/JSON) ที่ระบุสถานะที่ต้องการ

- **การสร้าง/อัปเดต**: ใช้คำสั่ง `kubectl apply -f [ชื่อไฟล์]`
    - ข้อดี: สามารถบันทึกประวัติไว้ในระบบ Version Control (เช่น Git), ทำซ้ำได้ง่าย และเป็นวิธีที่แนะนำสำหรับระบบ Production
- **การลบ**: แม้จะใช้ `apply --prune` ได้ แต่แนะนำให้ใช้ `kubectl delete -f [ชื่อไฟล์]` แทน

### 3. แนวทางแบบผสม (Hybrid Approach)

นักพัฒนามักใช้คำสั่ง Imperative เพื่อ "สร้างโครงไฟล์ YAML" ขึ้นมาโดยไม่รันจริง (ใช้แฟล็ก `--dry-run=client -o yaml > pod.yaml`) จากนั้นค่อยนำไฟล์นั้นมาแก้ไขและรันด้วยวิธี Declarative (`kubectl apply`) ซึ่งวิธีนี้มีประสิทธิภาพสูงมากในการสอบ

## GitOps และ Kubernetes

GitOps คือแนวปฏิบัติที่ใช้ Source code ใน Git เป็นแหล่งข้อมูลหลักในการจัดการโครงสร้างพื้นฐานโดยอัตโนมัติ โดยมีเครื่องมืออย่าง **Argo CD** หรือ **Flux** คอยดูแลให้สถานะในคลัสเตอร์ตรงกับที่ระบุไว้ใน Git ตลอดเวลา

---

## บทสรุป

Kubernetes ใช้ Primitives ในการทำงาน ทุก Object มีโครงสร้างมาตรฐาน (API version, Kind, Metadata, Spec) โดยมี `kubectl` เป็นเครื่องมือหลักในการสื่อสาร การใช้คำสั่งแบบ Imperative จะช่วยให้ทำงานได้เร็วในตอนสอบ ส่วนวิธี Declarative จะเหมาะกับงานที่ซับซ้อนและงานจริงในระดับ Production
