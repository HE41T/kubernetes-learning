# บทที่ 2: Kubernetes ในภาพรวม (Kubernetes in a Nutshell)

หากคุณยังใหม่ในสายงานนี้ การทำความเข้าใจภาพรวมว่า Kubernetes คืออะไรและทำงานอย่างไรนั้นถือเป็นเรื่องที่มีประโยชน์มาก  
แม้ว่าบนอินเทอร์เน็ตจะมีบทเรียนและหลักสูตรพื้นฐาน (101) อยู่มากมาย แต่ในบทนี้ผมต้องการสรุปข้อมูลพื้นฐานและแนวคิดที่สำคัญที่สุด  
ในระหว่างการอ่านหนังสือเล่มนี้ เราจะมีการอ้างอิงถึงส่วนประกอบของโหนดในคลัสเตอร์ (Cluster node components)  
อยู่บ่อยครั้ง ดังนั้นคุณสามารถกลับมาทบทวนข้อมูลในส่วนนี้ได้ตลอดเวลา

---

## Kubernetes คืออะไร?

เพื่อทำความเข้าใจว่า Kubernetes คืออะไร ก่อนอื่นเรามานิยามคำว่า "ไมโครเซอร์วิส" (Microservices) และ "คอนเทนเนอร์" (Containers) กันก่อน

- **ไมโครเซอร์วิส (Microservices):**  
  สถาปัตยกรรมแบบไมโครเซอร์วิสกำหนดให้มีการพัฒนาและรันส่วนประกอบต่าง ๆ ของแอปพลิเคชันแยกออกจากกันเป็นบริการย่อย ๆ และบริการเหล่านั้นต้องสื่อสารกันได้  

- **คอนเทนเนอร์ (Containers):**  
  หากคุณตัดสินใจรันบริการเหล่านี้ในคอนเทนเนอร์ คุณจะต้องจัดการคอนเทนเนอร์จำนวนมาก พร้อมกับต้องคำนึงถึงประเด็นสำคัญอื่น ๆ (Cross-cutting concerns) เช่น การขยายระบบ (Scalability), ความปลอดภัย (Security), การจัดเก็บข้อมูลถาวร (Persistence) และการกระจายโหลด (Load balancing)

เครื่องมืออย่าง **buildkit** และ **Podman** ทำหน้าที่แพ็กเกจซอฟต์แวร์ให้กลายเป็น "คอนเทนเนอร์อิมเมจ" (Container image)  
ส่วนโปรแกรมที่ใช้รันคอนเทนเนอร์ (Container runtime engines) เช่น **Docker Engine** และ **containerd** จะใช้อิมเมจเหล่านั้นเพื่อรันคอนเทนเนอร์  
ซึ่งการทำงานแบบนี้เหมาะมากสำหรับเครื่องของนักพัฒนาเพื่อใช้ในการทดสอบ หรือการรันงานแบบเฉพาะกิจ (Ad-hoc) เช่น เป็นส่วนหนึ่งของกระบวนการ **Continuous Integration (CI)**  
(สำหรับข้อมูลเพิ่มเติมเกี่ยวกับคอนเทนเนอร์ โปรดดูที่บทที่ 4)

**Kubernetes** คือเครื่องมือจัดการคอนเทนเนอร์ (Container orchestration tool) ที่ช่วยในการรันคอนเทนเนอร์จำนวนหลักร้อยหรือหลักพันบนเครื่องจริง (Physical machines),  
เครื่องเสมือน (Virtual machines) หรือบนคลาวด์ นอกจากนี้ Kubernetes ยังช่วยจัดการประเด็นสำคัญต่าง ๆ ที่กล่าวไปข้างต้นได้ด้วย  
โดยตัวรันคอนเทนเนอร์ (Container runtime engine) จะทำงานร่วมกับ Kubernetes เมื่อใดก็ตามที่มีการสั่งให้สร้างคอนเทนเนอร์ Kubernetes จะมอบหมายหน้าที่การจัดการ **วงจรชีวิต (Life cycle)** ให้กับตัวรันคอนเทนเนอร์เป็นผู้จัดการ

**หน่วยพื้นฐานที่สำคัญที่สุดใน Kubernetes คือ Pod**  
โดย Pod สามารถรันคอนเทนเนอร์ได้หนึ่งหรือหลายตัว พร้อมกับเพิ่มการจัดการด้านความปลอดภัยและความต้องการด้านทรัพยากรเข้าไป  
(ดูรายละเอียดเพิ่มเติมในบทที่ 5)

## คุณสมบัติ (Features)

หัวข้อที่ผ่านมาได้แตะถึงคุณสมบัติบางประการของ Kubernetes ไปบ้างแล้ว ในส่วนนี้เราจะเจาะลึกรายละเอียดของคุณสมบัติเหล่านั้น:

- **รูปแบบการประกาศเป้าหมาย (Declarative model):**  
  คุณไม่จำเป็นต้องเขียนโค้ดคำสั่ง (Imperative code) เพื่อบอก Kubernetes ว่าต้องทำอย่างไรกับแอปพลิเคชัน  
  สิ่งที่คุณต้องทำในฐานะผู้ใช้คือการ "ประกาศสถานะที่ต้องการ" (Desired state) ซึ่งสามารถกำหนดได้ผ่านไฟล์ YAML หรือ JSON ตามรูปแบบที่ API กำหนด  
  จากนั้น Kubernetes จะคอยดูแลรักษาให้ระบบอยู่ในสถานะนั้นและกู้คืนสถานะหากเกิดความผิดพลาด

- **การขยายระบบอัตโนมัติ (Autoscaling):**  
  คุณอาจต้องการเพิ่มทรัพยากรเมื่อแอปพลิเคชันมีภาระงานสูงขึ้น และลดทรัพยากรลงเมื่อทราฟฟิกลดลง  
  ซึ่งใน Kubernetes สามารถทำได้ทั้งแบบแมนนวลหรือแบบอัตโนมัติ วิธีที่ใช้งานได้จริงและมีประสิทธิภาพที่สุดคือการให้ Kubernetes ปรับขนาดทรัพยากรที่คอนเทนเนอร์ต้องการโดยอัตโนมัติ

- **การจัดการแอปพลิเคชัน (Application management):**  
  การเปลี่ยนแปลงแอปพลิเคชัน เช่น ฟีเจอร์ใหม่หรือการแก้บั๊ก มักจะถูกใส่ไว้ในอิมเมจคอนเทนเนอร์เวอร์ชันใหม่ (Tag ใหม่)  
  คุณสามารถอัปเดตการเปลี่ยนแปลงเหล่านั้นไปยังคอนเทนเนอร์ทั้งหมดที่รันอยู่ได้อย่างง่ายดายผ่านฟีเจอร์ **Replication** และหากจำเป็น Kubernetes ยังยอมให้คุณ **ย้อนกลับ (Roll back)** ไปยังเวอร์ชันก่อนหน้าได้

- **การจัดเก็บข้อมูลถาวร (Persistent storage):**  
  โดยปกติคอนเทนเนอร์จะมีระบบไฟล์แบบชั่วคราว เมื่อคอนเทนเนอร์รีสตาร์ท ข้อมูลทั้งหมดที่เขียนลงไปจะสูญหาย  
  แต่แอปพลิเคชันบางประเภทจำเป็นต้องเก็บข้อมูลไว้นานกว่านั้น เช่น แอปพลิเคชันที่ต้องทำงานกับฐานข้อมูล  
  Kubernetes จึงมีความสามารถในการเชื่อมต่อ (Mount) พื้นที่จัดเก็บข้อมูลที่จำเป็นสำหรับงานนั้น ๆ ได้

- **ระบบเครือข่าย (Networking):**  
  เพื่อรองรับสถาปัตยกรรมไมโครเซอร์วิส ตัวจัดการคอนเทนเนอร์ต้องยอมให้คอนเทนเนอร์สื่อสารกันเองได้  
  รวมถึงยอมให้ผู้ใช้งานภายนอกสื่อสารกับคอนเทนเนอร์ได้ด้วย Kubernetes จึงมีระบบ Load balancing ทั้งภายในและภายนอกเพื่อจัดการเส้นทางของทราฟฟิกในเครือข่าย

## สถาปัตยกรรมระดับสูง (High-Level Architecture)

ในเชิงสถาปัตยกรรม คลัสเตอร์ของ Kubernetes ประกอบด้วย **โหนดส่วนควบคุม (Control plane nodes)** และ **โหนดส่วนทำงาน (Worker nodes)**  
แต่ละโหนดรันบนโครงสร้างพื้นฐานที่จัดเตรียมไว้ไม่ว่าจะเป็นเครื่องจริง เครื่องเสมือน หรือบนคลาวด์ จำนวนโหนดและรูปแบบการวางตัว (Topology) ขึ้นอยู่กับความต้องการทรัพยากรของแอปพลิเคชัน

### ความรับผิดชอบของโหนดแต่ละประเภท:

- **Control plane node:**  
  - เปิดช่องทางติดต่อผ่าน API server และทำหน้าที่จัดการโหนดต่าง ๆ ในคลัสเตอร์  
  - ตอบสนองต่อเหตุการณ์ที่เกิดขึ้น เช่น เมื่อผู้ใช้สั่งเพิ่มจำนวน Pod เพื่อกระจายโหลด  
  - คลัสเตอร์ Production มักมี **High Availability (HA)** โดยมีโหนดส่วนควบคุมตั้งแต่ 3 โหนดขึ้นไป

- **Worker node:**  
  - ทำหน้าที่รันงานจริงในคอนเทนเนอร์ที่ถูกจัดการโดย Pod  
  - ต้องติดตั้ง Container runtime engine เพื่อใช้จัดการคอนเทนเนอร์

---

## ส่วนประกอบของโหนดส่วนควบคุม (Control Plane Node Components)

โหนดส่วนควบคุมต้องการชุดส่วนประกอบเฉพาะเพื่อทำหน้าที่ของมัน ดังนี้:

- **API server:**  
  จุดเชื่อมต่อ (Endpoints) สำหรับสื่อสารกับคลัสเตอร์ เช่น เมื่อใช้คำสั่ง `kubectl`  
  จะส่งคำขอแบบ RESTful API ไปยัง API server ซึ่งตรวจสอบสิทธิ์ (Authentication), ตรวจสอบการเข้าถึง (Authorization) และควบคุมการรับเข้า (Admission control)

- **Scheduler:**  
  กระบวนการเบื้องหลังที่คอยเฝ้าดู Pod ที่เพิ่งสร้างใหม่และยังไม่มีโหนดรันงาน จากนั้นจะเลือกโหนดส่วนทำงานที่เหมาะสมเพื่อส่ง Pod นั้นไปรัน

- **Controller manager:**  
  เฝ้าดูสถานะของคลัสเตอร์และดำเนินการเปลี่ยนแปลงเมื่อจำเป็น เช่น ปรับ Object ให้กลับสู่สถานะที่ต้องการ

- **Etcd:**  
  เก็บข้อมูลสถานะของคลัสเตอร์อย่างถาวร เพื่อให้สามารถกู้คืนข้อมูลได้หากโหนดหรือคลัสเตอร์หยุดทำงาน  
  เป็นซอฟต์แวร์โอเพนซอร์สแบบ Key-value store

---

## ส่วนประกอบร่วมของโหนด (Common Node Components)

ต้องมีในทุกโหนด ไม่ว่าจะประเภทใด:

- **Kubelet:**  
  รันอยู่บนทุกโหนด โดยหน้าที่หลักคือเชื่อม Kubernetes กับ Container runtime เพื่อให้แน่ใจว่าคอนเทนเนอร์รันอยู่ใน Pod อย่างถูกต้องและมีสุขภาพดี

- **Kube proxy:**  
  ตัวแทนเครือข่าย (Network proxy) บนทุกโหนด ดูแลกฎเครือข่ายและทำให้การสื่อสารเกิดขึ้นได้  
  มีส่วนสำคัญในการจัดการแนวคิดเรื่อง "Service"

- **Container runtime:**  
  ซอฟต์แวร์ที่จัดการคอนเทนเนอร์ สามารถเลือกใช้ตัวรันได้หลากหลายประเภท  
  แม้ติดตั้งบนโหนดส่วนควบคุมได้แต่ไม่จำเป็นเพราะปกติโหนดนั้นไม่ได้รันงานหลัก

## ข้อดี (Advantages)

- **การเคลื่อนย้ายได้ง่าย (Portability):**  
  อิมเมจคอนเทนเนอร์รวบรวมทุกสิ่งที่จำเป็นไว้หมดแล้ว ทำให้ Kubernetes สามารถรันแอปพลิเคชันได้ทั้ง On-premise หรือบนคลาวด์โดยไม่ต้องเขียนใหม่

- **ความทนทาน (Resilience):**  
  ออกแบบเป็นระบบสถานะแบบประกาศ (Declarative state machine) มีตัวควบคุมคอยตรวจสอบและปรับแต่งสถานะให้ตรงกับเป้าหมาย

- **การขยายขนาด (Scalability):**  
  สามารถปรับจำนวน Pod ตามความต้องการหรือทรัพยากรโดยอัตโนมัติ

- **ใช้งานผ่าน API (API based):**  
  ทุกการทำงานทำผ่าน API ทำให้ง่ายต่อการสร้างเครื่องมือใหม่ ๆ

- **การต่อขยาย (Extensibility):**  
  ชุมชนสามารถสร้างฟังก์ชันเพิ่มเติม เช่น ระบบ Monitoring หรือ Logging
